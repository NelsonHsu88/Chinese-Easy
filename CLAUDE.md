# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm install          # install deps
npm run start         # expo start — runs the Metro dev server, scan the QR with Expo Go
npm run android        # expo start --android
npm run ios             # expo start --ios
npm run web               # expo start --web (react-native-web target)
npx tsc --noEmit            # type-check the whole project — the closest thing to a build/verify step
npx expo-doctor               # validate SDK/dependency/config-plugin consistency
npm run check:env production    # assert a release build's env is present and carries no secret
```

`npm test` runs `src/**/__tests__/*.test.ts` on Node's built-in runner through `tsx` (a devDependency — Node 24 strips TypeScript natively but will not resolve this project's extensionless imports). Two suites, covering the two places where a quiet mistake is invisible until it has already cost the learner something:

- `lib/__tests__/srs.test.ts` — the FSRS scheduler. Bad scheduling maths costs weeks of reviews before anyone notices. **Every test fixes its own clock; none may read the real time**, both because a test that fails at midnight is worse than no test and because FSRS seeds its fuzz from the review instant.
- `lib/__tests__/placement.test.ts` — the placement test's fairness properties: that no answer option is ever another question's answer, and that the word set varies between attempts. Both were real defects, and neither is visible by looking at one question.

Everything else is unverified by any test. `npx tsc --noEmit` is the general check — run it after every change. The `lint` script in package.json (`eslint .`) is a leftover from before this project was migrated to Expo — eslint is not currently installed, so that script will fail until it's reconfigured.

A type-check is not a compile: NativeWind/Babel errors and bad `require` paths only surface in Metro. With the dev server running, ask it for a single module to check one without loading a browser —

```
curl -s -o /dev/null -w "%{http_code}" "http://localhost:8081/src/screens/Dictionary.bundle?platform=web&dev=true&minify=false"
```

200 means it compiled. This does not tell you anything about how it *looks*; a layout claim needs eyes on it.

`npx tsc --noEmit` does **not** cover the JS embedded in `src/components/HanziStage/writerHtml.ts`, which is a template string. To syntax-check that, extract the inline `<script>` body and run `node --check` on it.

### Asset pipeline

`scripts/` holds one-shot and re-runnable generators, all plain `node scripts/<name>.mjs`. They are not wired into any build step — output is committed, and a script is run by hand when its source material changes.

**Most of them read from `Photos for Reference/`, which is deliberately gitignored** (~225MB of full-resolution source art the app never loads). On a fresh clone those scripts cannot run until that folder is restored; their *outputs* under `src/assets/` are committed, so the app builds fine without it. Affected: `buildStoryCovers`, `processBuildingAssets`, `processUnitIcons`, `processCloudOverlay`, `extractSoftOverlay`.

- `buildStoryCovers.mjs` — resizes story cover art to 540×810 JPEG into `src/assets/images/covers/` and injects the matching `art:` field into `stories.ts`. Matches artwork to stories by the English title in each filename and **fails loudly on an unmatched file** rather than importing a partial set. Idempotent. Uses `sharp` (the only reason it's a devDependency).
- `processOnboardingArt.mjs` — prepares the onboarding watercolour (sakura, pagoda, mountain panorama, clouds) into `src/assets/images/onboarding/`. Unlike the other art scripts there is no keying to do — every source render already carries alpha — so it crops, trims and resizes. Two things it does that matter: it cuts 26px off the top of `mountains_landscape.png` (that render came back with stray sakura petals along its top edge, which would float in mid-air on the pages that anchor the panorama to the bottom), and it trims transparent margins, because an invisible margin is what the layout positions against and turns every offset into a fudge factor. Sources live in the gitignored `Photos for Reference/`; outputs are committed.
- `processDashboardArt.mjs` — prepares the Dashboard's watercolour (bowing Shifu, campfire, mountains, scroll, bonsai) into `src/assets/images/dashboard/`. Like `processOnboardingArt.mjs` there is no keying to do — these renders carry real alpha — so it trims and resizes. **The trim is the point**: every one of these sits in a card corner positioned against `right: 0` / `bottom: 0`, and an untrimmed render's transparent margin is what that offset actually measures from, so one illustration floats off the edge while another sits flush for reasons nothing in the stylesheet explains. It refuses a source with no alpha channel rather than emitting a black rectangle.
- `repairExampleSenses.mjs` — re-checks every example sentence in the word bank and fixes the ones showing a word in the wrong sense (see Word data). Unlike everything else here it reads only committed files, so it always runs; re-run it after `buildWordBank.mjs`.
- `processSubscriptionArt.mjs` — prepares the subscription screen's one new illustration (the thumbs-up Shifu) into `src/assets/images/subscription/`. Trim and resize, like the two above, and for the same reason: he is positioned against the hero's own edges, so an untrimmed render's transparent margin is what those offsets would be measuring. Everything else on that screen reuses art already in the bundle.
- `processReviewIcons.mjs` — prepares the Review hub's three drill icons into `src/assets/images/review/`. Unlike the corner decorations above, each of these is a **painted disc** dropped into the 58pt badge slot, so it trims *and then centres the result on a square canvas* — a disc a few pixels off-centre in a square box reads as a circle sitting crooked in its row, and the component can draw them at `width === height` and trust it. **It matches sources by their trailing `(N)`, not by name**: the exports are called `ChatGPT Image <timestamp> (1..3).png`, which says nothing about their contents, so the index→drill mapping was established by eye and is recorded in the script's `MAPPING`. Re-export the set in a different order and the icons silently swap — check the pictures against the comments before re-running.
- `generateSounds.mjs` — pre-renders every sound effect to WAV (see Sound below).
- `embedHanziWriterEngine.mjs` — regenerates `hanziWriterEngine.ts`; re-run after bumping `hanzi-writer`.
- `buildWordBank.mjs` — regenerates **both** word tiers (`src/data/importedWords.json` and `src/data/lookupWords.json`) from hand-downloaded CC-CEDICT sources in one run. Sources go in `.wordbank-data/` (gitignored; `WORDBANK_DATA` overrides) and the header lists every download URL. `cmn.txt` (the Tatoeba pairs) is **optional** — without it, existing example sentences are carried forward by word form, which is the normal path. Always follow with `repairExampleSenses.mjs`; see Word data for why that holds even when the sentences weren't rebuilt.
- `buildHanziData.mjs` — regenerates `src/assets/hanziData.json` from the `hanzi-writer-data` devDependency, covering every character in **tier 1** of the word bank, in **both scripts**, so stroke order works offline whichever script the learner chose. Re-run it after the word bank grows. Tier 2 is excluded on purpose — see the size note under HanziStage.
- `buildRadicalIndex.mjs` — regenerates `src/data/characterRadicals.json`, the character → Kangxi radical index behind the dictionary's Radical section, from the Unicode Unihan database (`Unihan_IRGSources.txt`; unzip Unihan.zip into `.wordbank-data/unihan/`, or set `UNIHAN_DATA`). Re-run alongside `buildHanziData.mjs` when the word bank grows — it seeds from `hanziData.json`'s keys, so it picks up both scripts automatically. It refuses to emit a radical number that `src/data/kangxiRadicals.ts` doesn't declare.
- `buildCharacterPinyin.mjs` — regenerates `src/data/characterPinyin.json`, a reading for every character the app can put in front of a learner, from Unihan's `kMandarin` (same hand-downloaded `Unihan.zip` and `.wordbank-data/unihan/` default as `buildRadicalIndex.mjs`). Two jobs: the pronunciation scorer turns arbitrary recogniser output into syllables with it, and `readingForText` uses it to put a reading under words the bank can't match. Both scripts are in there deliberately — a zh-CN recogniser writes back simplified — as is `stories.ts`, because story prose runs well outside HSK vocabulary and omitting it left one story segment in sixty with a blank line under it.
- `mergeHanziData.mjs` — superseded by `buildHanziData.mjs`; it read from a since-deleted `public/hanzi-data/` directory and cannot be re-run.
- `assertBuildEnv.mjs` — the one script here that is *not* a generator, and the only one wired into a build. It runs as `eas-build-pre-install` (also `npm run check:env`) and refuses a `preview`/`production` build whose `EXPO_PUBLIC_SUPABASE_*` values are missing, or whose `EXPO_PUBLIC_*` variables hold something that looks like a `service_role` key (the `sb_secret_` prefix, or a JWT whose payload claims that role).

  It exists because the runtime check in `lib/supabase.ts` is deliberately *soft* — an empty `.env` leaves the app running signed-out rather than crashing, so nobody working on another part of the project is blocked — and that softness is exactly wrong for a release, where `EXPO_PUBLIC_` values are inlined at bundle time and their absence produces a build that installs, opens, and cannot sign anybody in. Nothing in the pipeline noticed that before. `development` requires nothing, so local runs are untouched; the AdMob unit ids are deliberately not required either, since `.env.example` documents empty ones as a supported state.

When bumping dependencies, prefer `npx expo install <package>` (or `npx expo install --fix`) over plain `npm install` — it resolves versions against the current Expo SDK's compatibility matrix instead of npm's "latest". This project currently targets **Expo SDK 54**; `expo`, `react`, `react-native`, and every `expo-*`/`react-native-*` package must stay aligned to that SDK's versions (see `node_modules/expo/package.json`'s own dependency versions as the source of truth if `expo install --fix` doesn't cover something). `@react-native-community/datetimepicker` requires `npm install --legacy-peer-deps` — it has an optional peer on `react-native-windows` that npm's resolver treats as a conflict even though this project doesn't target Windows.

## Architecture

This is a React Native + Expo app (not a website) — a Duolingo-style Chinese learning app combining spaced-repetition vocabulary review, stroke-order writing practice, structured lessons, a reading library, and a light gamification layer (XP, streaks, daily/milestone challenges, an unlockable "My Town"). It runs on iOS, Android, and (via react-native-web) in a browser. **Both scripts are supported everywhere**: `settings.script` is a real preference (Settings → Learning preferences), stroke data is bundled for the traditional *and* simplified form of every word in the learning bank, and the reading library follows it too. Story content is authored and stored canonically in traditional (`src/data/stories.ts` is never rewritten), and Chinese story text is *displayed* in the learner's script — conversion is presentation-only and changes neither the stored story nor any vocabulary identity. See The reading design system for how that is done without breaking tap-to-look-up. The onboarding placement test follows it too — the character-script page is the second screen of onboarding precisely so the preference exists before the test runs.

### Feature flags — read this before assuming a screen is reachable

`src/lib/features.ts` (`FEATURES`) hides finished features rather than deleting them. **Both flags are currently `false`**, so two whole subsystems described below are built, compiled and unreachable in the running app: **Lessons** (`Lessons.tsx`, `LessonPlayer.tsx`, `/lessons`, `/lesson/[lessonId]`, `units.ts`, `lessons.ts`) and **My Town** (`MyTown.tsx`, `/my-town`, `townBuildings.ts`).

Consequences worth knowing before you debug something that "doesn't work":
- XP still accrues with My Town off, so a returning player's balance is intact when it comes back.
- The Lessons *tab* stays in the tab bar regardless — it's the only route to New Words and Books — but is relabelled "Learn" with a different icon, and its picker sheet drops the Lessons entry.
- `isRouteEnabled` / `safeRoute` let a link to a hidden screen degrade to a fallback instead of being deleted and later rewritten.

When re-enabling one, `grep` the flag name — the gates are deliberately scattered at each entry point (`(tabs)/_layout.tsx`, `Dashboard.tsx`, `MyWords.tsx`) rather than centralised, so each surface can degrade in the way that suits it.

### Routing vs. screen implementation

Expo Router is file-based, rooted at `src/app/` (not a top-level `app/` — Expo Router auto-detects `src/app` when there's no root-level `app/` dir). Files under `src/app/` are intentionally thin: each just re-exports the actual screen component from `src/screens/`, e.g. `src/app/dictionary.tsx` is `export { Dictionary as default } from '../screens/Dictionary'`. When changing a screen's UI/logic, edit the file in `src/screens/`, not the route file.

- `src/app/_layout.tsx` — root layout. Wraps everything in `AppProvider` (see below), loads fonts, and gates rendering: nothing renders (splash screen stays up) until `AppContext`'s `ready` flag and fonts are both true, then it redirects to `/onboarding` if onboarding isn't complete.
- `src/app/(tabs)/` — five `Tabs.Screen` slots (Dashboard, Lessons/Learn, Review, Dictionary, Settings), but only **Dashboard** (`index`), **Dictionary** (`dictionary-tab/`) and **Settings** actually switch tab content. The other two intercept `tabPress` with `e.preventDefault()` in `(tabs)/_layout.tsx`:
  - **Review** always pushes `/review` (the standalone route) — Review lives outside the tab chrome and provides its own back arrow, not actual tab content.
  - **Lessons/Learn** opens a `TabPickerSheet` (`/lessons` when that flag is on, plus `/new-words` and `/books`). This layout also owns `WritingGuideModal`, so the writing primer opens over the tabs rather than as a route.
  - `(tabs)/review-tab.tsx` is a redirect-only fallback that exists purely so `Tabs.Screen` has a route to point at. **Do not** name it (or the `dictionary-tab/` directory) `review.tsx` / `dictionary` — that would collide with the real standalone routes at `src/app/review.tsx` / `src/app/dictionary.tsx` (same URL path) and expo-router's navigator loops indefinitely instead of reaching the real screen.
- **`(tabs)/dictionary-tab/` is a nested `Stack`, not a single screen** — `index` plus `word/[wordId]` and `character/[character]`. That nesting is load-bearing and was arrived at by fixing two bugs: as sibling *tab* screens the detail views were switched to rather than pushed, so `router.back()` fell through to the first tab, and the Dictionary screen unmounted on the way out, losing the category filter and search query. Inside a stack the browse screen stays mounted underneath and the tab bar stays visible.
- Standalone routes pushed on top of the tabs (not nested in them): `/review`, `/review-session`, `/due-words`, `/onboarding`, `/profile`, `/dictionary`, `/new-words`, `/my-words`, `/my-town`, `/lessons`, `/lesson/[lessonId]`, `/books`, `/story/[storyId]`, `/challenges`, `/radicals`, `/subscribe`, and `/settings/{learning,reminders,goal,progress,general,developer,about}`.

`.expo/types/router.d.ts` is generated and does go stale — if a route that exists is reported as not assignable to `Href`, kill Metro, delete `.expo/types`, and restart rather than casting the path.

**Never write a bare `router.back()` on a screen's back arrow.** A screen reached by deep link, by a full reload of the web build, or as the first entry after a redirect has nothing to pop, and `back()` then silently does nothing — a back arrow that looks fine and is simply inert. Always `router.canGoBack() ? router.back() : router.replace('<parent>')`. `Books`, `NewWords`, `Review`, `ReviewSession`, `StoryReader` and `dictionary/DetailShell` are guarded; `Challenges`, `LessonPlayer`, `Lessons`, `MyTown`, `MyWords` and `Radicals` still are not.

### Review

`src/screens/Review.tsx` is the Review **hub** (route `/review`): a back arrow like the Lessons path, counters, and cards launching each drill. The drills themselves run in `src/screens/ReviewSession.tsx` (route `/review-session?mode=…`), pushed on top of the hub and closing back to it with `router.back()` rather than a push, so reopening drills doesn't stack duplicate hub entries. Modes are `flashcards` (due cards, the stroke-order writing flow), `listening` (multiple-choice audio recognition, `src/components/ReviewListening.tsx`), `mistakes` (cards with 2+ lapses), `full` (flashcards then listening) and `quick` (same as `full` but capped at 5 minutes). The session builds its whole step list once at mount — grading mutates the deck, so recomputing the queue mid-session would reshuffle it underneath the learner. Pool queries live in `src/lib/selectors.ts` (`weakCardsFor`, `mistakeCardsFor`, `listeningCardsFor`).

#### Review scheduling — FSRS

**Chinese Easy uses FSRS for long-term review scheduling**, via `ts-fsrs`. `src/lib/srs.ts` is the scheduling boundary and **the only module that imports `ts-fsrs`** — screens ask it for previews and commit grades through it, which is what made replacing the old SM-2 implementation a change to one file plus its callers rather than to every review surface. Don't scatter `import { fsrs } from 'ts-fsrs'` around.

The rules, which are product decisions rather than library defaults:

- **Again = failed recall.** The only rating that counts a lapse, and the only one that queues remedial writing reps.
- **Hard / Good / Easy = successful recall of increasing ease. Hard is a pass** — it records no lapse and does not drop the card into relearning. Never map a failed answer to Hard.
- **"I don't know" is Chinese Easy-specific and never reaches the scheduler.** No rating is submitted, no state changes, no lapse, nothing enters the review log. See the paragraph below for the session behaviour it does have.
- **The interval printed on each button is the interval that gets committed.** `previewReview` returns all four outcomes from *one* `repeat()` call and the caller passes that object back to `gradeCard`. This is not belt and braces: FSRS seeds its fuzz from the review instant, so recomputing when the button is pressed — a few seconds after the preview was drawn — lands on a different day. The button would say 4d and the deck would record 5d. There is a test asserting that drift is real, which will fail if the library ever stops depending on `now`.
- **Response time is analytics only.** It is recorded in the review log, capped at 60s so an abandoned card can't dominate an average, and never alters the rating or the interval. A slow Good is a Good.

Configuration lives in one place (`FSRS_CONFIG`): 0.90 desired retention, fuzz on, `1m 10m` learning steps and a `10m` relearning step. Retention is deliberately **not** a user-facing setting — it is the single number that decides how much work the app asks of someone daily.

`isCardDue` compares *instants*, not calendar days, because the learning steps are minutes: a card due in ten minutes is not due now even though it is due today. That also makes it immune to a device changing timezone or crossing a DST boundary, which comparing local dates was not.

**Persistence and migration.** `SrsCard` is schema **v2**: FSRS's own fields, snake_case and named exactly as the library names them, plus the app's `recentLapses` / `practiceQueue` / `practiceTotal`. Dates are ISO datetime strings and `lib/srs.ts` is the only place they are converted — JSON turns a `Date` into a string silently, and handing that string back to FSRS produces `NaN` arithmetic and a card that never comes up again rather than an error.

v1 was SM-2 (`intervalDays` / `easeFactor` / `stage`, `dueDate` an ISO date). `migrateDeck` runs on every hydrate and is a no-op once cards are v2. It is deliberately conservative: **due dates are preserved, so nothing that was not already due becomes due**, counts carry over, `stability` is estimated from the interval SM-2 had reached and `difficulty` is mapped off the old ease factor inverted. **No review history is fabricated** — v1 stored none, and inventing plausible entries would poison the very log a future parameter optimisation would read. The log starts empty and fills from here.

`mockDeck.ts` is still authored in the v1 shape and passed through `migrateDeck`, which exercises the migration every time anyone develops against a populated deck.

**Review modes needed no special handling.** All five (`flashcards`, `listening`, `mistakes`, `full`, `quick`) grade the same single card through the same `gradeCard`, so one word has one coherent schedule however it was encountered. The listening drill passes no preview — it never showed the learner four intervals to choose between, so there is no displayed number for the commit to match, and scheduling fresh at the moment of the answer is correct.

**"I don't know" never grades the card.** Both drills offer it (`onSkip` on `ReviewFlashcard` and `ReviewListening`); it appends a copy of the current step to the end of the queue and moves on, leaving the card's schedule untouched. Pressing "Again" to escape a word the learner has honestly not learnt would record a lapse against a card they never attempted, and teaches guessing over admitting. It re-queues **at most once per word per session** — without that cap, pressing it on the last remaining card extends the session by one every time and the end never arrives. The step `key` carries the index as well as the word id, or the second showing would reuse the first's mounted state (a flashcard still revealed, a question still answered). Appending a copy does not break the fixed-plan rule: the plan is fixed against the *deck* so grading cannot reshuffle it, and this re-queues something already in the queue.

The listening drill's verdict panel uses **`onbVerdict` from the onboarding tokens**, imported rather than re-picked — the same judgement should be the same colour wherever the learner meets it, and it carries the third state the drill needs: gold for "I don't know", which is deliberately neither green nor red because an honest admission is not a mistake.

The hub is built to its own reference mockup, over `src/components/review/tokens.ts` + `parts.tsx` (palette extended from the Dashboard's — see Per-screen design systems). Two things about the hero strip are geometry, not taste, and both were bugs first:

- **The speech bubble's width is derived, never hardcoded.** It is capped at `pagodaLeft - bubbleLeft - 8`, where `pagodaLeft` comes from `RANGE_SHARE`/`PAGODA_SHARE` — so the bubble is guaranteed clear of the pagoda at any screen width. A fixed `marginRight` measured against one window covers the artwork on every other one.
- The clearance rule is "clear of **the pagoda**", not "clear of the range". The range bleeds off the right edge and its faint left end is meant to sit under the text; treating the whole image as an obstacle is what left the strip mostly empty.

Unlike the Dashboard's staged score, everything in the Review entrance starts at once (`revEntrance` has a single `at`/`for`) — cards from the bottom, scenery from the right.

Each drill card's badge is a **painted disc** from `revArt` (`components/review/art.ts`), not a tinted circle with a glyph in it. The artwork carries its own circle, and each disc's colour is the `circle` value that drill's `revDrills` entry already had — which is why they dropped in without the cards being repainted. `DrillBadge` therefore sets no background and no radius: a coloured circle behind the image would only show as a rim of not-quite-the-same colour wherever the two disagreed by a pixel.

### State and persistence

`src/context/AppContext.tsx` is the single global store (settings, SRS deck, custom words, daily progress, streak, XP/unlocked buildings, completed lessons, newly-added-word flags, dev clock override, claimed challenges, dictionary recent-search history, per-story reading progress, onboarding state, the review log, New Words history), exposed via `useApp()`. All persisted state loads from AsyncStorage once on mount (`src/lib/storage.ts`); until that finishes, `ready` is `false` and the root layout keeps the splash screen up. Don't add new persisted fields without also adding them to the `hydrate()` `Promise.all`, the `skipNextSave` ref, and a guarded save `useEffect` (the guard skips saving the placeholder default on first render, before hydration has overwritten it) — follow the existing fields (e.g. `xp`, `completedLessonIds`) as the template.

**`newWordHistory` is the fix for a bug worth not reintroducing.** Skipping a word in New Words used to be a `Set` in that screen's own `useState`, so it lasted exactly as long as the screen stayed mounted — leaving and coming back put the skipped word straight back at the front of the queue, every time. A skip is a decision about a word, not about a screen, so it is persisted like everything else here: `{ wordId, outcome: 'skipped' | 'added', at }`, newest last, capped at `NEW_WORD_HISTORY_LIMIT`. The Recent sheet on that screen reads it and can unskip, which is what makes skipping cheap enough to be worth offering.

`reviewLog` is capped at `REVIEW_LOG_LIMIT` (5,000, oldest dropped) — enough to optimise FSRS parameters against later without one AsyncStorage value growing for the life of the install. See Review scheduling.

### Business logic vs. platform bridges in `src/lib/`

Split the module by whether it touches a platform API:
- Pure logic, safe to unit-test or reuse anywhere: `srs.ts` (the FSRS scheduling boundary — see Review scheduling), `selectors.ts` (deck queries — due cards, new-word pool), `date.ts`, `hanzi.ts` (simplified/traditional + pinyin/zhuyin display resolution), `zhuyin.ts`, `placement.ts`, `progress.ts` (heatmap/streak stats), `categories.ts`, `townEconomy.ts` (XP-per-grade/lesson, level curve, `canAfford` for My Town purchases), `challenges.ts` (daily/milestone challenge definitions + progress calculation), `textSegmentation.ts` (greedy longest-match word segmentation of story text against the word bank, for tap-to-add-word in the reader), `definitions.ts` and `dictionary.ts` (see Word data), `characterReading.ts`, `proficiency.ts` (the new/learning/proficient tiers in My Words), `pronunciation.ts` (see Speaking practice), `narration.ts` and `pagination.ts` (see The audiobook), `mandarinLocale.ts`, `features.ts`.
- Platform bridges, each a thin wrapper you'd swap if the underlying Expo API changed: `storage.ts` (AsyncStorage), `secureSessionStore.ts` (expo-secure-store — see below), `speech.ts` (expo-speech), `speechRecognition.ts` (expo-speech-recognition), `haptics.ts` (expo-haptics), `sound.ts` (expo-audio, playing pre-rendered WAV files — see below).

  **`secureSessionStore.ts` is where the Supabase session lives, and it is not `storage.ts`.** The distinction is the point: everything in `storage.ts` is app state, while the session is a **credential** — it carries a refresh token, and with `autoRefreshToken` on, that token mints new access tokens indefinitely. AsyncStorage is unencrypted on both platforms (a SQLite file on Android, a plain file in the iOS container), so anything that could read the filesystem read the token and *became that learner*. That was the only defect in this app that crossed from "your own data" to "somebody else's account", and it compounded with Android's default `allowBackup=true`, which swept the same file into the user's Google Drive — so `app.json` now sets `allowBackup: false` as well.

  Two things in that file are not optional. **The value is chunked**, because SecureStore refuses anything over 2048 bytes and a Supabase session is two JWTs plus the user record — writing it whole works right up until a provider attaches enough metadata, and then the learner is silently signed out on every cold start. The part count is written *last*, so a half-finished write reads as no session rather than a truncated one. And **web falls back to AsyncStorage**, because browsers have no keychain: `expo-secure-store`'s web shim is literally `export default {}`, so the `Platform.OS === 'web'` guard has to come before any SecureStore call, not after. Every failure path resolves to `null` rather than throwing — `getItem` returning null means "no session" to supabase-js, which signs the learner in again and recovers cleanly, whereas a rejection inside the auth client does not.

  `speechRecognition.ts` resolves its native module with `require` inside a `try`, not a static `import`. `expo-speech-recognition` calls `requireNativeModule` at module scope, which **throws** where the module isn't linked — including Expo Go, which only ships the modules in the Expo SDK. A static import therefore crashed the whole app on launch there instead of disabling one optional step. Every failure path in that file resolves to "not available" rather than throwing, because the caller's fallback (let the learner skip) is identical in every case.

  `mandarinLocale.ts` is shared by both speech bridges, and exists because **asking a platform engine for "Chinese" is not enough**: an engine with no voice or model for the exact tag falls back to any Chinese it does have, and on many Android builds that is Cantonese. It ranks Mandarin tags explicitly (`zh-CN` first — it's the tag engines most reliably map to Mandarin, ahead of `zh-TW` despite the app's traditional script) and hard-rejects the Cantonese ones.
- `devClock.ts` — a module-level override for "now" (set via Settings → Developer), used everywhere the app would otherwise call `new Date()` for streak/daily-progress logic, so streaks/challenges can be tested without waiting for real days to pass.

### Word data

**The dictionary is two tiers, and which one a word is in decides what the app is allowed to do with it.** Both are built by `scripts/buildWordBank.mjs` from the same CC-CEDICT source, in one run.

- **Tier 1 — the learning bank** (`src/data/importedWords.json`, 25,180 words, ~4.8MB). Frequency-ranked, so every entry has a meaningful `hskLevel`, a category, and where the corpus has one an example sentence. This is what the dictionary browses, what the SRS draws from, what `hskFrequency` exports, and what stroke data is bundled for.
- **Tier 2 — the reference tail** (`src/data/lookupWords.json`, 81,437 entries, ~4.5MB, read through `src/data/lookupWords.ts`). Everything else CC-CEDICT knows: chemical and medical terms, place names, institutions, classical idioms, and genuinely useful rarer vocabulary mixed in with them. **Findable by search, and nothing else** — not in `hskFrequency`, not in the SRS pool, not in the category browser, no stroke data.

106,617 words are searchable in total; a word you can think of is essentially always one of them.

Three things about the split are load-bearing:

- **Tier 1 is capped by the frequency list, not by CC-CEDICT.** Only ~26k of the 50k frequency entries exist in CC-CEDICT as pure-Han words with a usable gloss, so passing a `wordCount` above that has no effect — the loop runs out. Everything past that point is what tier 2 is for.
- **The two tiers are ranked in separate passes in `searchWords`, and appended.** Tier 2 has no frequency data, so `hskLevel` — the tiebreak that puts 蛋糕 above 糒 for "cake" — cannot order it against tier 1; scored into one list, 81,000 unranked rarities interleave with the vocabulary a learner wants. Ranking separately makes "tier 2 never outranks tier 1" a property of the control flow rather than a hope about the weights. Tier 2 is only consulted when tier 1 hasn't filled the page, so a search for "cake" never touches it and a search for "fovea" gets an answer.
- **Tier 2 is one packed string, split lazily.** Metro inlines JSON and parses it at startup, so 81k records would cost ~320k string allocations before the first frame. `lookupWords.ts` splits it — and folds a tone-stripped copy for matching, in one pass over the whole 4.5MB rather than per record — on the first search that reaches that far. `warmLookup()` is called from `Dictionary.tsx`'s mount so that ~100ms lands while the learner is reading the page rather than mid-keystroke.

Tier-2 entries carry id prefix `lk-` and `hskLevel === LOOKUP_HSK_LEVEL` (7, meaning "not ranked" — `HskBadge` prints "Rare" rather than inventing an HSK band). `wordById` falls through to `lookupWordById` for those ids, and AppContext's hydrate uses `wordById` rather than a set of `hskFrequency` ids — without both, a rare word added to My Words would be dropped as dangling on the next launch.

`src/data/hskFrequency.ts` merges a small hand-curated word list with a large bulk-imported dictionary (`src/data/importedWords.json`) into the full word bank. Both carry example sentences, but not uniformly: all curated entries have one (with pinyin), while roughly 6,200 of the 25,180 imported entries do (without pinyin). **Example sentences come from the bundled corpus and are never generated** — code that needs one filters for words that have it rather than inventing text (see `newWordsPool` in `selectors.ts`).

**An attached sentence has to contain the word, not just its characters.** `buildWordBank.mjs` matches Tatoeba sentences by substring, which in Chinese is not the same thing: 說 in CC-CEDICT's `shuì` "to persuade" sense came back illustrated by 別說謊, where 說 is `shuō` inside the word 別說. One attached sentence in five was wrong this way. `scripts/repairExampleSenses.mjs` is the corrective pass and **must be re-run after any rebuild of the bank** — it segments each sentence the way the app does and keeps the attachment only if the word survives as a token, drops any single-character entry whose reading is not that character's common one (no corpus signal can tell 說 shuì from 說 shuō), and swaps in the shortest sentence that genuinely contains the word where one exists. Coverage went 8,023 → 6,241 on the 20k bank, and 6,241 → 6,170 when the bank grew to 25,180; the losses were the wrong ones, and a word with no sentence is a supported state everywhere in the app. It is self-contained (needs only the committed JSON, not the hand-downloaded corpora) and idempotent against a fixed bank.

**"After any rebuild" includes a rebuild that did not touch the sentences.** The repair pass segments each sentence *against the bank*, so its verdicts depend on the bank's composition, not only on the corpus: growing tier 1 changed 110 attachments on sentences that had already been repaired once, because a word that used to survive segmentation now gets absorbed into a longer word the bank has since learned. `buildWordBank.mjs` also carries existing sentences forward by word form when `cmn.txt` is absent, which is the normal path — the corpus is only needed to *add* coverage, and re-deriving from it would throw away this pass's work.

The bulk bank is a whole dictionary, which shapes two rules in `src/lib/definitions.ts`:

- **Learning surfaces show `shortGloss(word)`, not `word.definition`.** CC-CEDICT lists every attested sense, so 會 arrives as seven of them — useless on a flashcard. `conciseDefinition` shows exactly **one**, and it is chosen rather than taken first: `senseScore` ranks every sense on plain-English grounds and the best one wins. The inputs are grammatical commentary ("used in…", "classifier for…", "lit. …") which is scored to the back; words absent from `src/data/commonEnglish.json` (a 10k English frequency list, so "alas" and "conflagration" are rare but "fist" and "reputation" are not); length; and position, which is weighted heavily enough that ~89% of entries keep CC-CEDICT's own first sense. Proper nouns are exempt from the rarity test and all-caps abbreviations are penalised by it, or 傑米 glosses as "Jim" and 結核病 as "TB". `plainEnglish` separately expands the dictionary shorthand (`sth`, `sb`, `esp.`) that has no business on a flashcard. The source data is never edited; the dictionary's *detail* card still renders every sense, one per line via `allSenses`.
- **`newWordsPool` gates on `isTeachableWord`.** Without it the New Words queue serves transliterated names (羅傑 "Roger"), surnames, abbreviations and bare grammar notes alongside real vocabulary. The proper-noun test is deliberately narrow — a lone capitalised word — so it rejects "Jack" while keeping "Good night!" and "United States". `src/data/mockDeck.ts` seeds a demo SRS deck; `src/data/placementTest.ts` is the fixed onboarding placement-test word list.

### Lessons, gamification, and My Town

*Lessons and My Town are both currently switched off — see Feature flags above. The code below is intact and compiled; only the ways in are hidden.*

- `src/data/units.ts` defines the Duolingo-style unit path (`UNITS`, 8 units). All 8 have authored lessons in `src/data/lessons.ts` (`LESSONS`, 25 total — 4 for `the-basics`, 3 each for the rest) mixing `match`/`scramble`/`fill-blank` exercise types. A unit unlocks once every lesson in the preceding unit is complete (`the-basics` is always unlocked), so `lessonsForUnit(id).length === 0` would silently make a unit permanently unreachable. Each unit also carries a `glyph` (hanzi character or emoji) shown in its path node. `src/screens/Lessons.tsx` renders the path, `src/screens/LessonPlayer.tsx` (route `/lesson/[lessonId]`) runs a single lesson's exercises.
- XP is earned from grading review cards (`xpForGrade`) and completing lessons (`XP_PER_LESSON`), and spent unlocking `src/data/townBuildings.ts` (`TOWN_BUILDINGS`, ordered, increasing `xpCost`) one at a time in `src/screens/MyTown.tsx` via `unlockBuilding`/`canAfford`. `levelForXp` (in `townEconomy.ts`) drives the shared level progress bar shown on both the Lessons path and My Town.
- `src/lib/challenges.ts` (`CHALLENGE_DEFS`) declares daily (reset-for-free via a date-suffixed claim id — see `challengeInstanceId`) and milestone (permanent claim id) challenges; `src/screens/Challenges.tsx` (route `/challenges`) shows progress and lets the user claim XP via `claimChallenge`. Each def also carries a `tone` (colour family for its tile and bar), `art`/`glyph` for the tile, and a `route` — tapping a challenge opens the screen where it can actually be worked on. Descriptions are rendered on **one line**, so keep them short; a long one is silently truncated.

  The screen is built to its own reference mockup and has its own design system in `src/components/challenges/tokens.ts` — colours, spacing, and the geometry of the card, hero and tabs. **That file is the only place a colour literal belongs**; the Tailwind config carries the matching shadows (`shadow-chal*`) and nothing else, because almost all of this palette is consumed by animated or state-dependent styles rather than class names. Typography is Nunito throughout (ExtraBold for headings, via `font-nunito-extrabold`), with Caveat standing in for the spec's Kalam on the handwritten reset note. `ChallengeCard` is one component with four states — `notStarted`, `inProgress`, `claimable`, `claimed` — and the mockup's "locked" state is deliberately not among them: nothing on this screen is ever locked, and a padlock would be telling the learner something untrue.

  **Claiming does not remove a challenge.** It collapses out of its position, then fades back in at the foot of the list at `CLAIMED_OPACITY`, where finished work stays visible without competing for attention. Two traps live in that move. The card mid-collapse is deliberately scored as *not* claimed so it holds its old slot until the animation ends — only then does the sort move it. And both halves are backed by a `setTimeout` as well as the animation's own callback: a non-native animation runs on requestAnimationFrame, which a browser stops dead for a hidden tab, so an app backgrounded mid-claim would otherwise come back to a row frozen in place still offering a Claim button for XP already paid out.

  Two web-only traps worth remembering beyond this screen: `onLayout` does not fire for every view under react-native-web, so never gate an animation on a measured height; and a `disabled` `Pressable` becomes `pointer-events: none`, which swallows clicks on everything inside it — that is why the finished card drops `onPress` instead of setting `disabled`, and it is what stopped Claim working at all.
- `src/data/stories.ts` (`STORIES`) is a hand-authored reading library — 46 stories across HSK 1-6, weighted towards the upper levels (folk tales, chengyu stories, festival legends and classical myths). Later stories set `pinyin: ''`: the reader renders a per-word reading from the word bank under each word, so a second romanised copy of the whole paragraph would be redundant and would have to be hand-checked syllable by syllable. Only `translation` is required on every page.

  Alongside the prose, each story carries card metadata: `titlePinyin`, `titleEnglish`, `description`, `collection` (which shelf it sits on — see `COLLECTIONS` in `components/reading/storyPresentation.ts`), an optional `art` cover, and `wordCount`. **`wordCount` is precomputed, not derived at runtime** — segmenting 46 stories against the 20k-entry word bank on mount is far too slow for a list screen. 31 stories have real covers; the other 15 fall back to a painted glyph tile, so an absent `art` is a supported state rather than a gap. `src/screens/StoryReader.tsx` (route `/story/[storyId]`) segments each page's Chinese text with `segmentText` (`textSegmentation.ts`) so known/unknown words are tappable; tapping an unrecognized word adds it to the deck via `addWordFromBook`, which also flags it in `newlyAddedWordIds` (surfaced as a badge dot on the Dictionary tab icon until `clearNewWordFlags` runs).
- Radicals come in three layers, and it matters which one you reach for. `src/data/radicals.ts` (`RADICALS`) is the **teaching** set: 99 of the 214 Kangxi radicals, each with an authored explanation, origin and worked examples, shown read-only in `src/screens/Radicals.tsx` (route `/radicals`) — not vocabulary words, never addable to My Words. `src/data/kangxiRadicals.ts` (`KANGXI_RADICALS`) is the **naming** table: all 214, reduced to number/glyph/pinyin/one-word sense/variants, so the other 115 still have something to print. `src/data/characterRadicals.json` is the **index**: every character in the word bank filed under its radical number, generated from Unihan. `radicalFor` in `src/lib/dictionary.ts` joins the three and is the only thing screens should call. Reversing `RADICALS` alone — what the dictionary used to do — knew the radical for 362 of 3,843 characters, so nine entries in ten showed no radical section at all.

### HanziStage — the stroke-order writer

`src/components/HanziStage/` is the one genuinely unusual part of this codebase. The `hanzi-writer` npm package draws stroke animations into real SVG/DOM and has no React Native port, so it runs inside a `react-native-webview`:

- `hanziWriterEngine.ts` — **auto-generated**, do not hand-edit. It's `hanzi-writer`'s minified UMD bundle copied into a JS string constant, produced by `scripts/embedHanziWriterEngine.mjs` from `node_modules/hanzi-writer/dist/hanzi-writer.min.js`. Re-run that script after ever bumping the `hanzi-writer` dependency.
- `writerHtml.ts` — the static HTML/JS every glyph's WebView loads. This is where the actual `HanziWriter.create()` call, demo/quiz lifecycle, and the "first stroke" hint overlay for blind quiz mode live (all DOM APIs, so they have to run here, not on the RN side). Also in here:
  - The Skritter-style **stroke-placement animation** — the newest stroke settles into position while completed ones stay put. Its displacement is converted from CSS pixels into the character's own 1024-unit space at runtime, because CSS transforms on an SVG path work in user units; a hard-coded `px` value would be nearly invisible.
  - **`strokeHint`**, posted on every miss at or past `HINT_AFTER_MISSES` (hanzi-writer offers no callback for the moment it highlights a stroke, so the same threshold is counted here) — HanziStage turns it into the gong.
  - **`holdCharacterOnComplete`**, which repaints the finished character in the stroke colour. hanzi-writer fades drawn strokes out the moment an animation or quiz ends, so without it the learner is left looking at the grey outline the instant they finish. It must be honoured in **both** the quiz and demo branches — it was originally only wired into the quiz, which is why the writing guide's animated centrepiece spent most of its time as a grey ghost. Opt-in, because the review flashcard deliberately wants the fade.
- `HanziStage.tsx` — the RN-side bridge. Looks up each character's stroke data (from the bundled `src/assets/hanziData.json`, falling back to the `hanzi-writer-data` CDN for characters not bundled, e.g. custom words), sends it into the WebView via `postMessage` once the WebView signals it's ready, and translates the WebView's posted-back events into the same `onQuizProgress` / `onQuizComplete` / `onDemoComplete` callback props the screens consume. One WebView is created per character in a word; multi-character words animate/quiz one character at a time.

`src/assets/hanziData.json` (character → stroke/median data) is the canonical bundled dataset, regenerated by `scripts/buildHanziData.mjs`. It covers **every character in tier 1 of the word bank, in both scripts** — 5,378 of them, ~15.8MB — so stroke order and writing practice work offline whichever script the learner chose. 165 characters have no stroke data in `hanzi-writer-data` at all (rare variant forms like 嵗, 偪, 説); for those, and for custom words, `HanziStage` still falls back to the hanzi-writer CDN and shows its error state if that fails too.

**Tier 2 is deliberately excluded**, and that exclusion is what keeps this file a manageable size. Bundling stroke data for every character CC-CEDICT knows would want ~11,700 glyphs and take the file to ~29MB, and 4,500 of those have no data upstream anyway. Tier 2 is a reference tail you look words up in, not vocabulary you practise writing — and a rare word added to My Words still gets the CDN fallback.

The file is large enough to matter: it is inlined into the JS bundle by Metro, so it is parsed at startup. If bundle size becomes a problem, the lever is narrowing the character set in `buildHanziData.mjs` (e.g. to the HSK levels actually reachable), not switching back to CDN-only — that would silently break stroke order offline for most of the bank.

### Animation — the traps, and the two reusable engines

The first three fail *silently*: the screen renders, nothing errors, and the result just looks like a layout bug.

1. **Use React Native's own `Animated`, not Reanimated.** Reanimated is a dependency (Gesture Handler needs it) but its update loop does not drive on this project's web target — an animated style evaluates once and then never changes, so an entering sheet sits permanently off-screen at opacity 0. Every animation in the app therefore uses `Animated` from `react-native`, with `useNativeDriver: Platform.OS !== 'web'`. Layout properties (`height`, `marginBottom`) can't use the native driver at all.
2. **NativeWind does not process `className` on an `Animated.View`.** The class string is dropped entirely — radius, padding, background, the lot. Always split: an outer `Animated.View` carrying plain styles and the transform, wrapping a plain `View` that keeps the Tailwind classes.

3. **An animated `transform` replaces the whole array — it does not merge.** A mirrored piece of art carrying `scaleX: -1` in its static `style` silently un-mirrors the moment an animation puts a `translateX` on the same view. Compose the static transform into the animated array instead (`useReveal`'s `extraTransform`), translate first so the offset is still measured in unflipped space.
4. **Every non-native animation needs a `setTimeout` backstop that force-sets its final value.** Without the native driver these run on requestAnimationFrame, which a browser stops dead for a hidden tab and whose timers it clamps to about one a second — so opening the app in a background tab otherwise leaves every entering piece parked off-screen at opacity 0, permanently. It only reproduces when the tab is not in front, which is why it is easy to ship. Every animation in the app carries one; see `dashEntrance.backstop`, `setTransition.backstop`, `Challenges.tsx`'s claim animation, and `Onboarding`'s `SlideIn`.

For an exit animation that closes the gap behind it (see `Challenges.tsx`), give each row its own `marginBottom` rather than a `gap` on the container — a collapsing row can't shrink a container's gap, so a hole is left behind.

5. **`useEntranceRun` skips the first focus, and must keep doing so.** Mounting already starts the score — every `useReveal` begins displaced and animates on its own mount effect — so ticking `run` on the focus that immediately follows restarted the whole thing a beat later. The screen faded a third of the way in, snapped back to the start and faded in again. The Dashboard's staged delays hid it; on a one-beat screen like Books or Challenges it was the animation visibly playing twice.
6. **A backstop has to cover anything the animation's *callback* does, not just the value it lands on.** `slideForward` in `ReviewSession.tsx` is the case that proves it: the entire session advance lived inside `Animated.timing(...).start(cb)`, so with rAF stalled the callback never fired and the session simply stopped — card frozen, buttons apparently dead, nothing to recover it. It now commits on whichever of the callback and a `setTimeout` arrives first, and the return leg carries its own backstop too.
7. **An entrance that replays on focus has to park itself on blur.** A focus effect runs *after* React has painted, so a screen left in its settled state shows one frame of itself already finished before the entrance yanks it back to the start — which reads as the screen loading, and then loading again. Both engines below leave themselves displaced on the way out (`useReveal`'s focus-effect cleanup, `useScreenTransition`'s), which is what makes the rest state the state a returning learner actually sees first. Same reason `useScrollToTopOnFocus` (`src/components/`) resets the offset on blur rather than only on focus: a mounted `ScrollView` keeps its position, and correcting it after the paint is a visible jump. It is on the Dashboard, Books and `SettingsShell`.

Two reusable engines exist; prefer them to a fresh `Animated.Value`:

- **`src/components/dashboard/entrance.tsx`** — an entrance score. `useEntranceRun()` returns a counter that ticks on `useFocusEffect`, so the scene replays every time the learner arrives rather than only on mount (a tab screen stays mounted underneath); `useReveal({ from, at, duration, run, distance, … })` plays one element's arrival off that counter; `useTypewriter(total, run)` returns a *character count* rather than a string, so the caller can slice rich text and keep the bold due-count inside the typed sentence.
- **`src/components/settings/transition.tsx`** — the screen-to-screen morph. `useScreenTransition()` returns a style plus `leave(go)`, and **`leave` plays the exit and then navigates**: pushing first mounts the next screen on top of an animation nobody sees. Content rises into place **from below** and leaves downwards, forward and Back alike — there is no left/right side any more, so the hook takes no argument. Its rest state is *displaced*, so arrival runs on **focus, not mount** — a category screen is pushed on top of Settings, which stays mounted with its content parked below the page, and would otherwise come back from a Back press invisible. `useLeave()` reaches the same exit from anything nested inside a shell (General → Developer), so screens don't thread a callback down by hand.

### The audiobook — narration and pagination

The story reader reads aloud with a transport bar (`components/reading/NarrationBar.tsx`: cover, title, ±5s, play/pause, scrubber) and a green line tracking the current word. Two things make that much harder than it sounds, and both are solved in pure-logic modules so the reader itself stays readable.

**A text-to-speech engine gives you no timeline** — no duration, no current time, nothing to seek. The only position signal is `onBoundary`, carrying the character offset of the word about to be spoken. `src/lib/narration.ts` rebuilds everything the transport promises from that one number: `createRateEstimator()` watches boundaries to learn the voice's real speed (clamped to 1.5–14 chars/sec, because engines batch boundary events and a pause at a comma can imply an absurd rate over a short window), and `skipTarget` converts ±5 seconds into a character offset snapped to the nearest word edge. `observeRun` is the calibration of last resort: a page spoken start to finish reveals the rate even from a voice that reported no progress at all, so the *next* page is predicted accurately.

**Chrome fires no `boundary` events at all for remote (network) voices.** This is why the green line once froze on the first word. `speech.ts` therefore scores voices with `REMOTE_VOICE_PENALTY` on top of the locale rank, so a local Mandarin voice wins even against a better-tagged remote one — and `StoryReader` still runs a clock-driven predicted-position ticker until the first real boundary arrives, because a voice that never reports progress must not mean a line that never moves. `pause()` is unavailable on Android, so pausing is a stop plus a resume from the recorded offset; the reader keeps a single `request` object (`{page, from, token}`) as the source of truth and speaks it under a `cancelled` flag, since web fires `end` on cancel too.

`src/lib/pagination.ts` re-cuts authored pages to screen size. Stories are written long (median 274 Chinese characters, up to 572) — several screens each, which meant scrolling and a translation stranded far from the text it explained. `paginateStory` packs whole sentences and carries the matching slice of the translation with each piece, breaking at commas and only then at a blind cut when a single sentence overruns a screen alone. The budget comes from `budgetForArea`, whose `CELL_WIDTH`/`CELL_HEIGHT` are **measured from the running app, not derived from the styles** — the computed row pitch was 68 against a real 77, which is a page and a half of drift over a story.

**A screen is `MIN_SENTENCES` (4) whole sentences, and the measured budget is a floor rather than a ceiling.** Sizing screens by the budget alone made books enormous: on a 393pt phone the reading area comes out at *sixteen characters* once the header, cover, translation card and page nav have taken their share, so the library was being cut into 1,654 screens — roughly fifty per story, a sentence at a time, with the progress bar showing 1% after the first turn. It is now 170 screens, three or four per story. The trade is deliberate and it is the promise that changed: a screen no longer claims to fit without scrolling (on a phone almost nothing does), it claims to be a few whole sentences with their translation. `MAX_SCREEN_CHARS` (300) stops "at least four" from meaning a 500-character screen, and it too breaks only at a sentence end. Both numbers are in `pagination.ts`; changing one is the whole knob.

### Speaking practice

`PronunciationCheck` grades **sound, not spelling**. It used to ask whether the recogniser's text contained the target's characters, which graded the engine's guess at meaning rather than the learner's mouth — say 謝謝 perfectly and be marked wrong because the engine wrote 寫寫. Both sides are now turned into syllables (initial, final, tone) and compared by `gradePronunciation` in `src/lib/pronunciation.ts`, passing at `PASS_THRESHOLD` (0.7).

The weights encode a policy, so change them deliberately: initial 0.45, final 0.40, tone 0.15, plus `EXTRA_TONE_ERROR` (0.15) charged for every tone error *after the first*. A homophone with the right tones scores 100%, one wrong tone in a two-syllable word 93%, both wrong 70%. **At a 0.7 threshold that last case now passes, on the nose** — the weights still rank tone errors, but the pass bar no longer separates one from two. Raise `PASS_THRESHOLD` back towards 0.8 if tone accuracy should gate progress again; that is the single knob for it. A neutral tone against a marked one is a half-error, because the bank writes 謝謝 as "xiè xie" while the per-character index reads both as tone 4, and neither the learner nor the microphone is really at fault there. The target is slid along the heard syllables and the best window wins, so a recogniser padding 謝謝 into "是謝謝" costs nothing.

`gradePronunciation` also returns `heard`, a flag per target syllable at `SYLLABLE_HEARD` (0.7). Interim results feed it, so on a multi-syllable word each character turns green as its syllable lands and the learner can see which part to aim at next. The flags only ever accumulate within an attempt: a later interim result can retract a syllable the engine had already committed to, and a character that goes green and then grey again reads as the app changing its mind about work you did.

### Sound

**`configureAudioSession()` must be called once at startup** (it is, from `src/app/_layout.tsx`). Without it iOS routes playback through the default audio session, where the ring/silent switch mutes everything — so every effect in the app is silent for anyone whose phone is on silent, which is most people most of the time. It also sets `mixWithOthers`, because a 200ms stroke click has no business pausing someone's podcast.

Haptics (`src/lib/haptics.ts`) have their own vocabulary and it is worth keeping to: `tick` for browsing detents (filter chips, segmented controls, a syllable landing), `tap` for something small picked up, `thunk` for weight (a page turned), `thud` reserved for the gong alone, and the sequences for genuine milestones. Note that **expo-haptics is a no-op on web** — nothing is wrong if a browser build feels dead; sound still plays there.

**In `sound.ts`, the rewind before `play()` must be awaited.** `seekTo` returns a promise, and a player that has finished sits parked at the end of its clip — where `play()` does nothing at all. Firing the seek without waiting therefore played against the end of the clip and fell silent, so every effect in the app worked exactly *once per launch*: one stroke click, one chime, and a gong nobody ever heard twice. The three stages (create, seek, play) each swallow their own errors on purpose, so a missing audio backend degrades to silence rather than an exception on a hot path.

`src/lib/sound.ts` plays short effects (stroke-scratch, positive chime, retry tone, tap, fanfare, gong) via `expo-audio`, from WAV files pre-rendered by `scripts/generateSounds.mjs` (there's no Web Audio API / oscillator synthesis available in React Native, so these are baked offline instead of generated at runtime). `AudioPlayer` instances are created lazily on first play, not at module scope — creating them eagerly crashes during Expo Router's static web render pass, where no audio backend exists yet.

The generator is a small synthesis toolkit, not just a list of beeps: the chime and gong are built from inharmonic partials with per-partial decay and run through `addRoom`, a Schroeder reverb (comb filters plus an allpass diffuser). Each effect's envelope sets its *shape*; its loudness comes from the `PEAKS` table, which every sound is normalised to on the way out — so clipping can't happen and the balance between the six is readable in one place. Tuned in isolation they had drifted 12dB apart, which is what made the stroke click inaudible next to the chime. Frequent effects (stroke, tap) sit deliberately below the one-off events.

### Example sentences

Every example sentence in the app renders through `src/components/dictionary/ReadingSentence.tsx`, which segments it with `segmentText` and puts each word's reading under that word — pinyin or zhuyin per `settings.phoneticScript`, taken from each matched word's own entry, falling back to `readingForText` (`src/lib/characterReading.ts`) for anything the bank can't match as a word. That fallback matters most in the reader, where 12.5% of story segments used to show a blank line: names, rare characters and bound forms are exactly the ones a learner needs the sound of. A matched word still wins, because its own `pinyin` knows which reading that word takes where the per-character index only has the commonest. Sentences therefore no longer print their `example.pinyin` field anywhere: it exists for only the curated slice of the bank, can't be aligned per word, and is pinyin even for a learner reading zhuyin. Pass `tone` to match the surrounding design (`dictionary` / `card` / `paper` — the app's three visual languages), and `onPressWord` only where the sentence isn't already inside a pressable card.

`segmentText` caches its lookup table against the bank it was built from. Without that, one call meant tens of thousands of map inserts, which was survivable when only the story reader used it a page at a time and is not when a modal segments sixty sentences. **The table is keyed on both scripts**, in one index rather than one per script: the text being segmented does not always match the learner's preference — story prose is authored traditional while an example sentence beside it follows the setting — so a single index segments either without the caller having to know which kind of text it is holding. Traditional is inserted first, so it wins a collision.

### Styling

**A percentage width inside a content-sized parent inflates that parent on native — `w-full` is not a safe way to say "as wide as this box".** Yoga resolves a percentage against the space the *parent* was offered, not the width the parent turns out to be, so a `w-full` child of a shrink-to-fit box measures the full width of the line and the box grows to hold it. This is what stacked the story reader's words one per row: `DottedUnderline` asked for `w-full` inside a word cell, every cell became a full-width row, and the page turned into a column of single words. It reproduces on a phone only — react-native-web treats the same percentage as `auto` while it is measuring a shrink-to-fit box, so the browser laid the identical tree out correctly. Use `alignSelf: 'stretch'`, which asks for the width the parent turns out to have instead of voting on what it should be.

**A `shadow-*` class draws nothing on Android.** NativeWind compiles `boxShadow` to the iOS `shadowColor`/`shadowOffset`/`shadowRadius`/`shadowOpacity` props, and Android draws shadows from **`elevation`** alone — which no Tailwind class sets. So every `shadow-dict` / `shadow-paper` / `shadow-chal` surface is flat on Android. The token *objects* (`dashShadow`, `dashShadowLifted`, `setShadow`, `revShadow`) all carry an `elevation` and are the ones to reach for when a surface must look raised on both platforms; the classes are fine for anything where the shadow is a nicety. This is why the dictionary's speech bubble had to move from `shadow-dict` to `dashShadow`.

NativeWind v4 — Tailwind classes on RN components, configured in `tailwind.config.js` (brand/coral/amber color scales, `font-sans`/`font-hanzi` families) and `babel.config.js`/`metro.config.js`. Dark mode follows the OS color scheme automatically (NativeWind syncs to `useColorScheme()` on its own); there's no manual dark-mode toggle code. `react-native-reanimated` v4 requires `react-native-worklets/plugin` in `babel.config.js` (not the older `react-native-reanimated/plugin` — the babel plugin moved packages in Reanimated v4).

**Fonts are registered one family per weight.** React Native can't synthesise weights the way a browser can, so `NunitoBold`, `NunitoBlack`, `InterMedium`, `NotoSerifTCSemiBold` and so on are each loaded separately in `src/app/_layout.tsx` and mapped to their own `fontFamily` key in the Tailwind config. Setting `fontWeight` on its own does nothing useful — pick the family instead. This matters most for CJK, which has no synthesisable bold at all.

The hanzi families come in four groups and the distinction is intentional: `font-hanzi*` (serif, SC fallback in front for anything that might not be traditional), `font-hanzi-tc*` (serif, traditional-only), `font-hanzi-sc*` (serif, simplified-only), and `font-hanzi-sans*` (Noto Sans TC, for the writing guide, whose Chinese has to sit beside sans-serif UI type).

**A screen that follows `settings.script` picks its face through `hanziFont` (`lib/hanzi.ts`), never through `font-hanzi`'s fallback chain.** The chain does cover both character sets, but Noto Serif SC and TC draw a good many shared codepoints differently (骨 and 直 among them), so an SC-first chain hands a traditional learner mainland glyph forms for most of the screen. `hanziFont` maps the preference to `hanzi-tc-*` or `hanzi-sc-*`, and it **spells both class names out as literals** — Tailwind finds classes by scanning source text, so a template literal generates no CSS and every hanzi silently falls back to the system serif. Kangxi radical glyphs are the exception and stay on `hanzi-tc-*`: they come from the `KANGXI_RADICALS` reference table, not from a bank entry with two forms.

#### Per-screen design systems

Screens redesigned from reference mockups each own a `tokens.ts`, and **that file is the only place a colour literal belongs** on those screens — they're built largely from inline style objects and animated styles rather than class names, and two sources for one palette is how a screen ends up with five nearly-identical greens. They fall into two groups:

- **Self-contained palettes**, deliberately unlike the rest of the app: `challenges/`, `onboarding/`, `writingGuide/`, and the `read-*` scale in the Tailwind config (Books / Story Reader).
- **The ivory-and-jade family**, which is one room rather than four: `dashboard/tokens.ts` is the base, and `settings/tokens.ts` and `review/tokens.ts` both extend it (`setShadow = dashShadow`, `revShadow = dashShadow`, palettes spread from `dashColors`). The dictionary's `dict-*` Tailwind scale is the same family expressed as class names. Settings sits behind the same tab bar as the Dashboard and is reached from it constantly — the two must not look like different apps.

All of these are **light-only**. The design rests on warm paper under watercolour; a dark repaint would be a different design, not a recolour, so they carry no `dark:` variants.

**Every full-screen layout caps its column at 430 and centres it** — `DASH_CONTENT_MAX`, `SET_CONTENT_MAX`, `REV_CONTENT_MAX`, `DICT_CONTENT_MAX`, `ReadingShell`, and the writing guide's `CONTENT_MAX`. These are phone-sized objects: uncapped on a desktop browser, a search field runs a foot across and a two-column word list becomes two 400pt cards. When a new screen "looks like a responsive website", check for a missing cap before touching any padding — that was the entire cause on the Dictionary. Size decoration and inner columns against `Math.min(windowWidth, …_CONTENT_MAX)`, never against `useWindowDimensions().width` directly, or the art scales with the window rather than with the design.

**Vertically the rule is the opposite: fill the height, don't cap it.** A screen laid out to its natural height leaves everything the device has spare as a band of bare paper under the last element. The fix is never to enlarge components — it is `contentContainerStyle={{ flexGrow: 1 }}` on the `ScrollView`, `flexGrow: 1` on the column, and `FlexGap` (`src/components/FlexGap.tsx`) where a section margin would have gone. A `FlexGap`'s `min` is a `flexBasis` **and a `minHeight`**, so when the content already overflows there is no free space to share, every gap sits at its designed value and the page just scrolls — which is why this is safe to add and why **it changes nothing on a phone-sized viewport**. The `minHeight` is not belt and braces: the basis alone measured zero on Android, so every gap on the Dictionary collapsed and the quick-links card was drawn hard against the bottom of the search field while the same screen on web sat at the designed 40. A floor no flex maths can talk down is the only reliable form of this component. `max` is what keeps a hole from opening in the middle instead; leave it off only for a gap inside a bounded card. `vspace` (`src/lib/verticalSpace.ts`) is the same idea for a single dimension — the JS equivalent of `clamp(126px, 11.5dvh, 148px)`, and its `share` is deliberately tuned so every phone lands on the `min`.

Each screen needs one deliberate slack absorber or the space merely moves to the bottom of the last capped gap. On Review it is the button-and-artwork block, which grows uncapped so the bonsai and petals pinned to its bottom ride down and terminate the page; on the Dictionary it is the two-column word region, whose cards stretch while the rows inside them do not — the slack collects above each card's footer action, which is whitespace inside a card rather than under the whole interface.

### Onboarding

`src/screens/Onboarding.tsx` — seven screens (welcome, **character script**, goal, account, reminders, placement test, ready), built to reference mockups, with a fourth visual language in `src/components/onboarding/tokens.ts`. As with the challenges and writing-guide token files, **that file is the only place a colour literal belongs**; light-only, for the same reason.

- **Every page is three regions: top bar, flexible middle, stable footer** (`OnbShell`). Only the middle grows. That is what keeps the primary button on the same line across all seven screens instead of walking up and down the page as the learner advances, and it is why the middle is a `ScrollView` with `flexGrow: 1` — it fills a tall screen and still scrolls on a short one rather than collapsing to its content.
- **Page order lives in one array, `STEP_ORDER`, and both indicators derive from it.** Inserting the script page after welcome moved every dot along without a number being edited anywhere — so add a page there rather than renumbering by hand.
- **There are no numbered step pills.** The footer dots are the flow's only progress indicator. `OnbSteps` used to draw "1 2 3 4" above the script page and the placement test and has been deleted; two indicators saying the same thing in different units, disagreeing about how many steps there are, was worse than one.
- **Decoration is absolutely positioned and allowed to bleed off the edge** (`PageArt.tsx`). A mountain panorama placed as a normal flex child consumes layout height and shoves the footer around; out of flow it costs nothing. Art also ignores the 22pt content margin on purpose — a branch that stops inside the margin reads as a sticker, one clipped by the screen edge reads as a branch. `ArtLayer` carries `pointerEvents="none"` for the whole layer (an `Image` does not accept the prop), or a corner branch swallows taps on Skip.
- The sakura render grows left-to-right from a trunk at its bottom-left. The top-right placements mirror it with `scaleX: -1` rather than shipping a second 200kB copy.
- `Shifu.tsx` is **a stand-in**. The references use three painted watercolour renders (waving, bowing beside a bell, thumbs-up in confetti) that don't exist yet, so each pose is assembled from the flat vector `mascot-shifu.png` plus props. It is one component with a `pose` prop precisely so the real art replaces it by swapping the source, with no page layout touched.
- **The welcome screen never scrolls** (`scroll={false}`), and the mascot is the one element with give — `<Shifu fill>` flexes into whatever height the header, card and footer leave. That needs **`minHeight: 0` on the flexed `Image` and its wrapper**: a flex item defaults to `min-height: auto`, which refuses to shrink below its content, and an Image's content is its intrinsic pixel height. Without it `flex: 1` reclaims nothing and the page overflows by exactly the amount the mascot should have given up.
- **The welcome screen animates in** — branch from the left, mountains and pagoda together from the right, mascot and footer up from the bottom, all fading 0→1 on one `Easing.out(Easing.cubic)` and staggered by `onbMotion.enterStagger`. `SlideIn` in `parts.tsx` does it; `fill` puts the wrapper on `position: absolute; inset: 0` so it can carry absolutely-positioned scenery without either knowing the other's coordinates.

- **Pages hand over via `OnbPageTransition`**, which wraps whatever `renderPage()` returns: the arriving page mounts first and the page being left slides off over the top of it, forward to the left and Back to the right, uncovering the new one already rising into place. The first page deliberately does not animate, because the welcome screen has its own staged entrance and playing both made it move twice.

  **The order is the fix for a bug, not a preference.** The two halves used to be strictly sequential — empty the screen, *then* mount the next page — so every millisecond of that mount was spent looking at bare cream paper. Because every element on these pages sits inside an entrance wrapper, a page starts at opacity 0 with nothing static to hold the screen, and on a phone in a dev build that read as the app having hung for a second or more between steps. Mounting underneath means the mount happens while the old page is still on screen, and the exit runs on the native driver, so it keeps moving smoothly even while the JS thread is busy building what is behind it. The exit is started from an effect *after* the commit that mounts the arriving page, so a slow page reads as a beat of delay before the change rather than as a blank screen in the middle of it.

  Keeping both pages alive needs **two fixed slots**, each page staying in the one it arrived in — a single slot whose contents swap would remount the leaving page and replay its entrance as it slid away. Both slots are absolutely filled, and **the spare one must carry `pointerEvents="none"`**: an absolutely-filled `View` is a hit target in React Native whether or not it has anything in it, so left on `auto` it lies over the whole page and swallows every tap. Neither slot takes touches mid-change, which is what stops a second tap landing on the arriving page's button before the learner can see it. The old warning about a two-up carousel re-running the previous step's effects does not apply: the leaving page is the tree that was already mounted, held as a stale snapshot, and the placement test's speak-on-arrival effect lives in `Onboarding` itself rather than in the page tree.

  **Every non-native animation in this flow carries a `setTimeout` backstop that force-sets its final value** (`SlideIn`, `ResultToast`, `OnbPageTransition`). Without the native driver these run on requestAnimationFrame, which a browser stops dead for a hidden tab — so opening the app in a background tab leaves every entering piece parked at opacity 0, off-screen, permanently. Same defence, and the same reason, as the claim animation in `Challenges.tsx`. It is easy to miss because it only reproduces when the tab is not in front.
- **The character-script page comes second, before anything else asks a question**, and that position is the whole point: the placement test below reads `settings.script`, so the preference has to exist before the test runs. It writes the **one global `settings.script`** via `updateSettings` — the same field Settings → Learning preferences owns — and seeds its local selection from it, so a resumed onboarding shows what is actually stored. There is deliberately no onboarding-only copy of the preference.

  `OnbScriptCard` (in `parts.tsx`) is a taller shape than `OnbChoiceCard` because the glyph *is* the question: someone who reads neither script decides by looking at 學 beside 学, so the two have to be big and adjacent. Each is drawn through `hanziFont(script)` so 學 gets the TC face and 学 the SC one — rendering either through the other's font is the one thing this page must not do. Selection reuses the choice cards' crossfade (mint fill and jade border on one non-native driver, since border colour cannot run native and the halves must not desynchronise), and `tickHaptic` fires **only on a real change** — a tick for re-tapping the selected card teaches people to distrust the feel.

  Shifu here is `fill`, and the flexed wrapper is **outside** `OnbRise`. `OnbRise` renders a content-sized `Animated.View`, so a `fill` mascot inside one has no slot to shrink into and gets clipped through the face by the footer on a short phone. `align="start"` puts him at the left edge, at the foot of the range, rather than centred in it.

- **The placement test is multiple choice**, not self-rating, and comes in three kinds. `src/lib/placementQuiz.ts` builds them: **meaning** (word shown, pick the gloss), **listening** (the word is spoken and the options are hanzi, with no pinyin anywhere on the prompt — a romanisation is a transcript of the thing being tested; it speaks itself on arrival and offers a replay button), and **cloze** (one of the bank's own example sentences with the word cut out, pick what fills the gap). Cloze is the only kind that tests a word *in use*: a learner can know that 因為 means "because" and still not know where it goes.

  **Cloze sentences come from the bank and are never invented.** A word qualifies only if its example contains it *exactly once* — twice would leave two gaps and one answer, which the learner would be right to call unfair — and anything that fails falls through to the listening/meaning rota. All 50 curated words qualify today, in both scripts.

- **The word set is sampled per attempt, not fixed.** `samplePlacementItems(seed)` draws `ITEMS_PER_LEVEL` (3) from each HSK level's curated pool of 8–10, so the *shape* of the test is constant — three words a level, easiest level first — while the particular words vary. The old eighteen hard-coded ids were the same for everyone in the same order, memorable after one sitting and shareable. Level order is preserved deliberately: `computeEstimatedHsk` reads the run of levels the learner got right, and a test that opens on an HSK 6 word tells a beginner they are out of their depth before they have answered anything. The seed is fixed for the life of the attempt, so stepping back finds the same question with the same options, and the estimate is computed against exactly the items the questions were built from.

- **Wrong answers must never be a word the test also asks about.** They come from `placementDistractorPool(items)` — the curated words this attempt does *not* ask about. Drawing them from the tested items, which is what this used to do, hands the learner a free elimination: a word that has already been the answer to its own question cannot be the answer to a later one, so every question answered made the rest easier and the estimate drifted high — placing a beginner too high, which is the direction that hurts most.

  Two further rules, both of which were defects first:
  - Candidates are ordered **nearest HSK level first** (a seeded shuffle, then a stable sort by level distance), so options vary between attempts but an HSK 6 word never sits beside an HSK 1 answer — that gives the answer away as surely as a repeat.
  - Exclusion matches on the rendered **label**, not the word. 高興 and 快樂 both reduce to the gloss "happy", so excluding tested *words* alone still let an untested one print a tested one's label and put the elimination back. Matched per kind: glosses for meaning, hanzi for listening and cloze.

  There is a fallback to the old same-pool behaviour if the distractor pool ever runs short. It should never fire — three slots against five-plus spare words at every level — and `src/lib/__tests__/placement.test.ts` asserts across five seeds and both scripts that it doesn't, that no option is ever another question's answer, and that every question has four distinct options with exactly one right one.
- **Answering is two steps: pick, then Confirm.** Options stay uncoloured until the answer is committed — colouring on tap would make Confirm pointless and let the learner shop for the green one. Confirming raises a `ResultToast` above the footer and the button becomes Next question. There is also an **"I don't know"**, which skips straight to the verdict.
- The three verdicts live in `onbVerdict`: green correct, coral incorrect (coral *is* this palette's red — a pure #FF0000 would look like an error dialog from another app), and **gold for "I don't know"**, which is deliberately neither. `computeEstimatedHsk` is unchanged and still speaks in ratings: correct records `know`, everything else `unknown`. A wrong guess and an honest "don't know" are worth the same to the estimate but are told apart in the toast, because punishing the honest answer teaches the learner to guess.
- `GoogleMark.tsx` is the real four-colour G as four SVG paths. The first attempt built it from a rotated ring with four coloured borders, which reads as a Google logo at a glance and as obviously wrong on any closer look — and this is a button people recognise by its mark, so a near-miss is worse than none.
- `settings.learningGoal` is the one new persisted field. It rides along in the existing settings blob, which hydrates as `{...DEFAULT_SETTINGS, ...loaded}` — so it backfills for existing users without any of the separate-field plumbing described under State and persistence.

### The writing guide

`src/components/WritingGuideModal.tsx` — "How to write Chinese", a four-page primer opened from the Learn tab's picker sheet (so it renders over the tab chrome rather than as a route). Each page pairs one idea with one character animated live by the same writer the practice screens use, which teaches a rule far better than a numbered diagram of it — that's the whole reason it's a screen and not help text.

- It is the app's **third visual language**, defined in `src/components/writingGuide/tokens.ts` — warm cream, exactly three greens, surfaces built from border-plus-tint rather than shadow. As with `challenges/tokens.ts`, **that file is the only place a colour literal belongs**, and for the same reason: this screen's surfaces are mostly inline styles rather than Tailwind classes, so stray hex values are how you end up with five nearly-identical greens. Light-only, like the reading screens.
- `writingGuide/parts.tsx` holds the shared pieces (`GuideProgress`, `ExampleCard`, `PlainCard`, `TakeawayCard`, `SpeedSegment`, `PrimaryButton`); `WritingGrid.tsx` is the 米字格 practice square; `RuleList.tsx` carries `STROKE_RULES`.
- **Tapping a rule swaps the character in the grid above it** rather than expanding inline. That keeps the layout as drawn, and means one animation on the page instead of five WebViews stacked in a list.
- **No page scrolls.** The character is the only element with any give — everything else is type and cards at fixed sizes — so the grid is sized from the height left over rather than from the column width alone: `GRID_SHARE` per page, floored at `GRID_MIN`, capped by `GRID_RATIO` of the column. It is *per page* because the pages are not equally full; one shared ratio meant either a tiny character on page one or a scrollbar on page three. `CHROME` is measured from the running app, not derived from the styles — the same call `pagination.ts` makes, for the same reason. The `ScrollView` stays as an overflow safety net for unusual devices or large accessibility text; when the content fits, it never scrolls.
- **Only page one asks the learner to write** (`TRACING_PAGE`). Tracing is how that page proves its point — you cannot feel that a character is built in a fixed order by reading it. Pages two and three are about recognising things, so their button says "Got it" and simply advances; making the learner trace 媽 again to get past a sentence about radicals is a toll, not a lesson. The pencil icon follows the label, so "Got it" carries none — an icon promising a writing pad that never opens is worse than no icon.
- The column is capped at `CONTENT_MAX = 430` to match `ReadingShell` — uncapped, the writing card stretches to a desktop window's width and its guides end up drawn into one corner of a very wide rectangle. The card is a centred square at `GRID_RATIO = 0.56`, deliberately narrower than the cards beneath it so the page doesn't read as a stack of identical panels.
- `WritingGrid` draws its own guides instead of using `HanziStage`'s `showGuides`, because this grid belongs to the card: paler than the writer's built-in one, and inset from the card's rounded border rather than filling the writer's box. It passes `holdCharacterOnComplete` — without it hanzi-writer fades the drawn strokes out the instant the animation ends, leaving the page's green centrepiece as a faint grey outline most of the time.

### The Dashboard

`src/screens/Dashboard.tsx` composes five components from `src/components/dashboard/` — hero, Review, New Word, Challenges summary, This Week — over its own design system in `tokens.ts`. As with `challenges/`, `onboarding/` and `writingGuide/`, **that token file is the only place a colour literal belongs**, and it is light-only for the same reason: the design rests on cream paper under watercolour.

Things worth knowing before changing it:

- **Every card carries an illustration positioned past its own edge.** `CardArt` is absolutely positioned with `pointerEvents="none"` and derives its height from a ratio in `art.ts` — React Native does not size an `Image` from its intrinsic dimensions the way a browser does, so a width with no height lays out at zero and the artwork silently vanishes. Those ratios describe the *trimmed* asset, so re-running `processDashboardArt.mjs` may mean updating them.
- **A card can be one pressable *and* several, but only through `PressClaim`.** Nesting a Pressable inside a Pressable double-fires on the web target: the event bubbles from the inner handler to the outer one, so a tap on "Add this word" would add the word *and* push the route. `PressClaim` (in `dashboard/parts.tsx`) is what makes the combination safe — an inner press marks its ancestors before the event finishes bubbling, and the card's handler stands down when it sees the mark. Every `PressableScale` claims automatically; anything hand-rolled must call `usePressClaim()` itself, which is why `CardLink` does. The flag clears on a `setTimeout(…, 0)` rather than after the press, because web bubbles synchronously (so the outer handler still sees it) while native never fires the outer at all (so nothing else would ever clear it, and the next press on the card body would be eaten).
- Which cards use which shape: Review and Challenges are a single target, their "Start Review" pill and "View all" label plain Views following the press through `usePressProgress()`. The word card is the combined case — body opens New Words, with See all / Not now / Add this word keeping their own actions.
- **`PressableScale` takes layout on `wrapperStyle`, not `style`.** `flex` on the inner Pressable does nothing while the `Animated.View` around it is still sized to its content — which is how the word card's two buttons ended up overlapping each other.
- The greeting's handwritten name is **Kalam** (`font-handwritten`), deliberately a different family from the reading screens' Caveat (`font-handwriting`): Caveat is a connected slanted script, Kalam an upright marker hand. It sits on `BrushHighlight` with `fleck={false}` — the detached fleck reads as a stray rectangle behind a word this long.
- The hero clips Shifu at the hem via `overflow: hidden` rather than shipping a pre-cropped render, and mirrors both the sakura branch and the pagoda range with `scaleX: -1` to put their trunks and roofline on the right. The branch is sized to clear **"Good Afternoon,"**, not "Good Morning," — the longest greeting is the one that has to fit.
- **The This Week card opens `/settings/progress`** — the same story over twelve weeks. It needs no transition of its own: `DetailShell` already rises into place on `useScreenTransition()`, so pushing that route from the Dashboard gets the fade-in for free.
- `currentWeekActivity` (in `lib/progress.ts`) backs the This Week strip. It is a *calendar* Monday-to-Sunday week rather than the heatmap's rolling `lastNDays(7)`, because the strip is labelled M T W T F S S and a rolling window would move Wednesday's dot overnight. It distinguishes a missed day from one that has not happened yet.
- **Setting `tabBarStyle.height` opts the bar out of safe-area handling.** The height React Navigation computes for itself is base + `insets.bottom`; overriding it with a bare number puts the tab bar underneath Android's gesture pill or three-button nav, which then intercepts the taps. `(tabs)/_layout.tsx` therefore derives `70 + Math.max(insets.bottom, 12)` with a matching `paddingBottom` — the floor covers a device reporting no inset, and the inset itself covers everything else (~48dp for Android 3-button, 34 for an iPhone home indicator). Any future change to that height has to keep the inset term.
- The bottom tab bar draws its own icon *and* label inside `tabBarIcon` with `tabBarShowLabel: false`, because the active pale-green pill has to wrap both and React Navigation renders them as separate siblings. Tabs 4 and 5 keep their real labels (Dictionary, Settings) rather than the reference's Progress/Profile, which name screens this app does not have.
- **`WeeklyActivityCard` and `WeekSparkline` share one axis, derived once.** The strip's seven dots and the chart's seven x-positions are both laid out from the same column arithmetic, inset by `dashWeek.gutter` (which is what the chart's y-tick labels live in). They drifted apart once already, with a comment claiming they matched. The y-tick labels are RN `<Text>` positioned over that gutter rather than SVG `<text>`, so they use the card's font stack and don't scale with the viewBox.
- **The entrance is a staged score in `dashEntrance`** (scenery → greeting → cards → Shifu → bubble → typing), played by `entrance.tsx`. Shifu deliberately starts *before* the cards finish, so he reads as rising out of them. See Animation above for the machinery.
- **Buttons here are two-part objects, not shadowed pills.** `LiftedFace` (in `parts.tsx`) draws a "shoulder" at `top: DASH_LIFT` carrying the shadow, with the face translating down onto it by exactly `DASH_LIFT` on press — which is why they look depressed rather than merely dimmed. Shoulder colours live in `dashShoulders`; they are chosen, not derived, because "a shade darker" is a judgement about this palette. Start Review, "Add this word" and "Not now" are all the same object at different sizes. It reads the press from a `PressProgress` context via `usePressProgress()` rather than owning a `Pressable`, which is what lets it work both as a button that is its own target *and* as the pill inside a card that is the target — nesting a second `Pressable` double-fires on web.

### The ad-free subscription

`src/screens/Subscribe.tsx` (route `/subscribe`) is one screen in two states, built to its own pair of reference mockups over `src/components/subscription/` (`tokens.ts`, `art.ts`, `parts.tsx`). Which state shows is decided by `isAdFree` in `AppContext` and by nothing else.

- **There is no IAP package in this project, and `src/lib/subscription.ts` is the seam where one goes.** A real store is *registered* (`registerStore(adapter)`), never imported — Metro resolves a literal `require` at build time whether or not it runs, so a `require('react-native-iap')` for a package that isn't installed fails the bundle, and a native purchase module would throw on import in Expo Go and take the app down on launch. Wiring a real store is: install the package, write a `NativeStore` adapter, call `registerStore` once at startup. Nothing in the screen changes.
- **The screen never grants on a button press.** `applyEntitlement` is called from the *outcome* of `purchasePlan`/`restorePurchases`, never from `onPress`. With no store registered there are exactly two honest behaviours and no third flattering one: in `__DEV__` the purchase is simulated and the screen says so where the renewal terms would go (`source: 'simulated'` is carried on the entitlement and surfaced in both the purchase footer and the status card); in production it declines with `unavailable`. Restore reports finding nothing rather than inventing something.
- **`isAdFree` is the single source of truth.** Do not add an `isPremium` anywhere — an entitlement two screens disagree about is a learner who has paid on one and not the other. The stored entitlement is trusted at launch so the state survives offline, then `currentEntitlement()` is asked and the store's answer wins.
- Prices come from the store where there is one; `FALLBACK_PRODUCTS` ($4 / $36) is display fallback only, and the store-cancellation wording follows the platform (`storeName()`) rather than saying "the App Store" on Android.
- **The screen raises itself every five minutes** (`useSubscribePrompt`, mounted in the root layout beside `TourOverlay`). Foreground time only, never during onboarding, a lesson, a story or a review session, never over itself, and never once entitled. The clock is held while the screen is open, so closing always buys a full interval of quiet. Raised this way the corner control is a **close** rather than a back arrow (`?prompt=1`) — there is nothing behind an offer nobody asked for. Settings → Ad-free is the permanent way in.
- **The hero is the only element that changes size**, and it is given `available height − contentBelow` rather than a share of the window: `subHero.contentBelow` is measured from the running app, per state, the same call `lib/pagination.ts` and the writing guide make. That is what makes the page end at the bottom of the screen instead of in a band of bare cream, and what makes a short phone shrink the artwork before it scrolls. Re-measure it if anything below the hero changes height.
- Decoration is absolutely positioned inside the clipped hero and layered back to front (range → branch → petals → Shifu → bubble); everything functional is a plain flex column. The button is the Dashboard's `LiftedFace`, not a second implementation, and the marker stroke under "ad-free" is the app's `BrushHighlight` — one flourish on the page and no more.
- Only one new asset was needed (`processSubscriptionArt.mjs` → `subscription/shifu-thumbs-up.png`); the bowing Shifu, the pagoda range, the branch and the closing panorama are the Dashboard's and onboarding's own art, reused.

### The Settings screens

`src/screens/Settings.tsx` is a hub of grouped cards; the actual controls live in seven screens under `src/screens/settings/` (`LearningPreferences`, `Reminders`, `GoalSettings`, `ProgressOverview`, `General`, `Developer`, `About`) behind thin routes in `src/app/settings/`. Shared pieces are in `src/components/settings/` (`tokens.ts`, `parts.tsx`, `cards.tsx`, `transition.tsx`).

- **Moving a control off the hub never removes it.** Everything the old single-page Settings did still exists, including the developer date/time override (`devClock`) — it just moved to `settings/developer`.
- **`settings/developer` is `__DEV__`-only, in two places, and must stay that way.** The controls behind it are not diagnostics, they are cheats: the simulated clock re-arms every daily challenge (`challengeInstanceId` is date-suffixed), fabricates a streak, and resets the interstitial day cap in `lib/ads/frequency.ts`, while the entitlement toggle grants ad-free outright. Shipped, that is a learner rewriting their own progress *and* the ad policy from the Settings screen — and once `FEATURES.cloudSync` is on, syncing the fabrication to the server as history.

  Both halves are needed. `General.tsx` wraps the Advanced row in `{__DEV__ && …}` so there is no way in, and `Developer.tsx` opens with `if (!__DEV__) return <Redirect href="/settings/general" />` because hiding a link does not stop a deep link to `chineseeasy://settings/developer`. That guard sits **above every hook**, which is safe here and only here: `__DEV__` is a build-time constant, so the branch is fixed for the life of the bundle and React's hook order can never change under it.

  This does not cost on-device testing, which is what the original ungated comment was protecting: `__DEV__` is true in Expo Go and in any `eas build --profile development` client, so the screen is still there on a phone throughout development. It is false only in store builds, where Metro's dead-code elimination strips the whole UI — verified by bundling `src/screens/settings/Developer.bundle` at `dev=false&minify=true` and finding none of its strings, against three occurrences at `dev=true`. That is the check to re-run if this is ever touched; note that requesting `expo-router/entry.bundle` proves nothing, because routes are split into their own bundles and none of the screens are in it.
- **Nothing requests a native permission on mount.** Opening Reminders must not ask for notification permission; only the learner explicitly enabling reminders may.
- **Chinese script is a real picker again**, not the `LockedRow` it was while stroke data covered traditional only. It now governs the reading library as well as vocabulary, so the hint no longer carves out an exception for stories.
- There is deliberately **no "Offline" row**, despite the mockup having one — the app has no download feature, and a toggle that does nothing is worse than an absent one. That slot is the About/licences screen instead.
- The hub and every category screen wrap their content in the shared morph transition (see Animation). A new settings screen gets `useScreenTransition()`, exactly as the hub does — **content rises from below and leaves downwards on every screen in the group**, so there is no side to pick and the hook takes no argument.

### The Dictionary

`src/screens/Dictionary.tsx` is the browse screen inside the `dictionary-tab/` stack (see Routing). Its palette is the `dict-*` Tailwind scale — warm ivory under jade, matching the Dashboard/Settings family; it was originally a cool-grey SaaS-dashboard system and must not drift back. Lucide takes a colour prop rather than a class, so `ICON_MUTED`/`ICON_GREEN`/`ICON_GREEN_DARK` in `DictionaryControls.tsx` shadow three of those Tailwind values and have to be changed in step with them.

- `DictionaryControls.tsx` holds the shared controls, under two rules: **haptics fire on release, when something actually changed** (a feel on press-in fires even when the finger slides off), and **sound is reserved for adding a word** — navigating, filtering and opening an entry are silent.
- **The screen has its own entrance score in `dictionary/entrance.ts`** (`dictEntrance`), played by the Dashboard's `useReveal`. Three beats in the order the screen reads: the page rises as one piece (Review's single-beat feel, because a dictionary is one object rather than six unrelated cards), then Shifu, then his line types on. The typing is *faster* than the Dashboard's — `useTypewriter` takes optional timing precisely so it can be — because this sentence is nearly a hundred characters against the Dashboard's forty, and at the same pace the learner finishes reading long before Shifu finishes writing.
- **The browsing header is Shifu, not the landscape.** `DictionaryIntro.tsx` puts him beside a speech bubble saying what the screen is for. That replaced `HeaderScene`'s ink-wash landscape *and* the standfirst under the title — a heading, a subtitle and a picture were three things answering one question, on a screen whose complaint was clutter. `HeaderScene` is still exported and still used for `CornerWash` (the faint card-corner art) but the landscape itself is no longer drawn anywhere. Both washes are absolutely positioned and `pointerEvents="none"`: in flow they'd push the search field down the page, and a decoration that swallows a tap is a bug. Heights are computed from each source's ratio, because RN lays out an `Image` with a width and no height at zero.
- **Search ranking is a ladder, in `SCORE` in `lib/dictionary.ts`, and the English tiers are the part that matters.** English matches used to share one score, so the tie fell through to *character count* — a ranking by obscurity, since a rare single character always wins it. "cake" put 蛋糕 seventh, under 塊 ("classifier for pieces of cloth, cake, soap etc"); "rice" put 價格 "price" above 米飯. Four tiers now separate a sense that *is* the query from one containing it as a word, as the start of a word (which is what makes search-as-you-type work: "dumpl" has to find "dumpling"), and as bare letters. Ties break on sense index, then `contentRank`, then **`hskLevel`** — which is derived from a frequency rank when the bank is built, so it genuinely means "the word they probably meant".
- **An exact English gloss outranks a loose pinyin match, and that ordering is deliberate.** A pinyin prefix counts as a reading only when it lands on a syllable boundary (`isSyllablePrefix`): "shui" of "shuǐ guǒ" is someone typing a word, "red" of 熱帶's "redai" is a coincidence of spelling, and before this the coincidence won — "red" answered with 熱帶, 熱點 and 熱度, and 紅色 was nowhere. Same fix put 巴士 above 不是 for "bus".
- Plurals are folded on the *query* (`singularise`), not the entries: CC-CEDICT glosses in the singular, so "dumplings" used to return nothing while "dumpling" returned 餃子. Both forms are tested, so a bad guess can only add candidates.
- **Per-entry scoring work is cached in a `WeakMap` (`fixedKeys`)** — folded reading, syllables, lowercased definition, split senses, content rank. Folding a reading is a Unicode normalise plus a regex, and it was being redone for all 20,000 entries on *every keystroke*: a typical query went from ~45ms to ~4ms. Keyed by the entry object, so a rebuilt bank is new keys rather than stale ones.
- **HSK level is a filter button beside the search field, not a row of chips.** Six chips took a whole band of the page to say one number; the button carries the current level on its face and opens the chips in a panel only when asked. Picking a level closes the panel, because the answer is then on the button and showing it twice is just the old row again.
- **The two narrow cards are one shape twice.** `ColumnCardHeader` and `ColumnCardAction` exist because the pair sit side by side and the learner reads *across* them: when only the starter column had a See-all row, its list started a row lower than "Recently added" and nothing below lined up again — and one footer was a bare text link over a rule while the other was a filled pill, so the card bottoms disagreed too. Both now carry title → See all + count → rows → `FlexGap` → the same pill. Verify by measuring, not by eye: the two footers and the two See-all rows should share a `y` exactly.
- **`adjustsFontSizeToFit` is iOS-only — never rely on it to stop CJK clipping.** The stroke-order sheet's resting character used a fixed 120pt with that prop and `numberOfLines={1}`; on Android the prop does nothing at all, so any word wide enough simply lost its tail off the edge. Three characters clipped on every phone narrower than a Pro Max, four clipped everywhere. It now derives the size: CJK glyphs are full-width so a character's advance is ~1em, which makes `availableWidth / charCount` a good bound, capped at the design's 120 and against window height. `HanziStage` already did the equivalent for the *animated* state (`perCharSize`), which is why only the at-rest glyph was affected.
- **`PressScale` puts `style` on the animated view and `className` on a plain view inside it** — the dictionary's version of the `PressableScale` trap above. The inner view carries `flexGrow: 1` so a height passed in `style` is one the visual view actually fills; without it that view stays content-sized and sits at the *top* of the animated one, which silently makes any `justify-center` in `className` a no-op. That is what left every category tile's icon and label hard against the top edge with 39pt of blank tile beneath.
- The category tiles have **no fixed height** — icon, label and padding, nothing else. A fixed 96 was 39pt taller than the contents. All six hold one line, so self-sizing keeps the row level. The 78pt *width* is still fixed and still load-bearing: it puts four and a bit tiles on a 390pt screen, so the row visibly continues and invites a swipe.
- **The three quick links are stacked, not rows.** Side by side, a third of the column left ~50pt for the label, so "My Words" (needs 64) and "Radicals" (53) arrived truncated. The chevron went with the row — three tiles already read as pressable, and it was costing width the label needed. Check this by measuring `scrollWidth` against the rendered width rather than by eye; at the 430 design cap the clipping is easy to miss.
- Sizes are tuned for a ~390pt screen, not for a browser window: category tiles are 78×96 so four and a bit are visible and the row obviously continues, word rows are 44pt tiles on a 12pt gap, and the whole column caps at `DICT_CONTENT_MAX`. Judge changes at phone width.

### The reading design system

The Books, Story Reader and Challenges screens share a second, later visual language from the reference mockups, deliberately distinct from the rest of the app: cream paper, dark-ink type with a hint of navy, watercolour illustration and restrained pastel accents.

#### Story text and the script preference

**Stories are stored canonically in traditional and displayed in the learner's script. The conversion is presentation-only — `src/data/stories.ts` is never rewritten, and no vocabulary identity changes.**

The whole design rests on one ordering: **segment first, convert second.** `segmentText(text, wordBank, displayScript)` matches the canonical traditional prose against the bank, then converts each segment's *display* form, leaving `text` (canonical) and `word` (the matched `VocabWord`) untouched. So a simplified learner tapping 学校 gets the same entry as a traditional learner tapping 學校, and every dependent feature — dictionary lookup, deck status, the coral "not yet added" dots, the reading under each word, `addWordFromBook` — keeps working without knowing conversion happened. Converting the string up front instead would segment simplified text against a traditional index and silently kill the match on every word whose forms differ.

`TextSegment` therefore carries three fields with three jobs: `text` is canonical and is what offsets are measured from, `display` is what you draw, `word` is identity. Draw `display`; measure and look up with the other two.

**Conversion comes from the word bank first and a character table second**, both generated by `buildWordBank.mjs` from CC-CEDICT:

- A matched segment takes its own entry's `simplified` field — CC-CEDICT's phrase-level answer, and the same data the dictionary will show when the word is tapped. That covers 92% of the Han characters in the library and is what gets the context-dependent cases right (頭髮 → 头发, where 髮 and 發 both reduce to 发).
- Everything else falls to `src/data/scriptConversion.json` via `lib/scriptConversion.ts` — 117 character occurrences across all 103 story pages. **Only trad → simp is emitted, because only that direction is safe per character**: simplified 干 stands for 乾, 幹 and 干, and choosing needs the surrounding word.
- That table is built by **aligning each word's two forms character by character and taking the commonest mapping**, not by reading CC-CEDICT's single-character rows. The rows look like the obvious source and are wrong for characters with two simplified forms: taking 乾's first row gave 乾淨 → 乾净, a word in neither script. The build prints any character where the two sources disagree (40 today).

**Two invariants hold this together, and the build enforces the first rather than trusting it.** Conversion never changes character count — `buildWordBank.mjs` exits non-zero rather than emit an entry whose two forms differ in length — which is what lets the narration cursor, `segmentSpans` and `paginateStory` keep counting canonical characters while something else is drawn. And the aligned character table is only meaningful *because* of that same equal-length property.

Consequences worth knowing: pagination and `storyProgress` (a page index) are computed from canonical text, so switching script cannot move a page boundary, reset progress or duplicate a story. The narrated text *is* converted — safe for the same length reason, and worth it because `mandarinLocale` ranks `zh-CN` first and a zh-CN voice is the one most likely to stumble on a traditional-only character. Fonts come from `hanziFont(script, weight)`; the reading screens use the `medium` weight, which is `hanzi-tc` (Noto Serif TC) or `hanzi-sc` (Noto Serif SC).

- Colours live under a `read-*` namespace in the Tailwind config, kept separate because they intentionally overlap the older `brand`/`coral`/`amber` scales with warmer, less saturated values. **Don't mix the two.**
- Shadows are `shadow-paper` / `shadow-paper-lifted` / `shadow-paper-sheet` — broad, faint and tinted warm rather than black. `shadow-glow-jade` / `shadow-glow-paper` are the deliberate exception, reserved for the buttons a learner is meant to act on.
- Type: Nunito for headings, Inter for UI, Noto Serif TC for hanzi, Lora for English prose in the reader. The Chinese and the UI must not share a face.
- `src/components/reading/` holds the shared pieces: `ReadingShell` (cream page capped at the 430pt design width), `PageDecor` (ink-wash range and drifting clouds), `StoryArt` (cover, with the painted glyph fallback) and `storyPresentation.ts` (shelves, palettes, progress). `BrushHighlight` (in `src/components/`) draws the handwritten marker stroke as SVG — at most one handwritten note per screen.
- **These screens are light-only.** The design rests on cream paper; a dark repaint would be a different design rather than a recolour, so they don't carry `dark:` variants.
- **Books and Challenges arrive on their own animation, not the navigator's.** The whole page fades up from `ENTER.rise` on one ease-out curve (`useReveal`, replayed each focus), and both routes set `animation: 'none'` so the stack's push slide isn't running underneath — two transitions at different speeds read as a stutter rather than as either one, the same call `DetailShell` makes. On Challenges this wraps the claim animation without competing with it: the entrance plays once on the way in, the claim fires on a tap long after it has settled.
